# R2 holdout designs: leave room for memory to matter

## Scope and mechanical constraints

This is a paper design. I did not use the network, run a model, execute a company, or modify the
dataset or either roster repository. The only implementation artifact is this report.

The designs assume the intended post-migration contract in the request: required behavior is
scored from `expected.structured_fields`, while `expected.forbidden` remains a text safety check.
There is a current integration gap to close before these YAML fragments are literally executable:

- `company_memory_study.py` still loads `expected.required` and calls `score_text`, with no
  structured field on `MemoryCase`
  (`src/fabri/benchmarks/company_memory_study.py:62-65,194-218,871-876`).
- `company_setup_probe.py` currently loads `expected.structured`, not
  `expected.structured_fields` (`src/fabri/benchmarks/company_setup_probe.py:491-499`). Its scorer
  itself has the desired recursive subset-equality semantics
  (`src/fabri/benchmarks/company_setup_probe.py:1002-1034`).
- None of these three company roots declares a `response_schema`; absent migration-time schema
  injection, a run returns no `structured_output`. The requested structured-field migration must
  therefore both align the dataset key and arrange a response schema without exposing the
  expected values. If it injects the expected enum values or constants into the holdout context,
  it destroys the headroom proposed here.
- The evolution loader still requires prose `expected.required` for all three variants
  (`src/fabri/benchmarks/company_evolution.py:338-375`). The revised variants below are designs for
  the same structured-scoring migration, not something to run through that old loader unchanged.

The transport is otherwise exactly suitable. Training and holdout are separately compiled
(`src/fabri/benchmarks/company_memory_study.py:611-620,719-751`); the memory arm copies only the
declared SQLite DBs (`:775-795`), while the control removes DBs and has both mining and retrieval
disabled (`:744-751,796-815`). Mutable training workspaces cannot carry the convention. The
compiled root is explicitly told to preserve durable decisions and reusable lessons in its
machine-readable memory block (`src/fabri/company.py:19-35`), and the root company collection uses
the shared SQLite DB with `top_k: 5` and postmortem recording enabled
(`src/fabri/company.py:290-318`). That is the channel each design deliberately uses.

The central pattern is the same in all three cases: training establishes an evidence-to-decision
protocol and applies branch A; holdout supplies fixed workspace evidence for branch B without
naming the schema keys or branch values. Echoing the training decision therefore fails. A useful
memory must retrieve the mapping and apply it.

## `support_hq_safe_incident_response`

### (a) What the training run establishes

Training uses the account-specific duplicate-charge ticket to establish the `SHQ-E1` customer
evidence protocol. It defines four decision axes and two branches:

- A customer assertion without operational corroboration maps to `REPORT_ONLY`, `DIRECT_REPLY`,
  `CUSTOMER_FACTS`, and `VERIFY_ACCOUNT`.
- Observed multi-customer service impact followed by rollback and return to baseline, without
  evidence of a permanent remedy, maps to `MITIGATED`, `EXTERNAL_STATUS`, `CLASS_ONLY`, and
  `MONITOR_UPDATE`.

The training run applies the first branch to Maya's duplicate-charge report and is explicitly told
to put the exact mapping and identifiers in the root memory block. The second branch is defined but
not the training answer.

This is grounded in the actual crew. Support HQ has a support macro report and an incident
postmortem report (`/Users/rushour0/gba/fabri-rosters/companies/support-hq/company.toml:15-26`). The
support drafter can read files and is instructed not to invent policy or behavior
(`/Users/rushour0/gba/fabri-rosters/agencies/support-macro-writer/drafter.openai.yaml:5-15`), and its
ticket really is an unverified request about two charges and a possible refund
(`/Users/rushour0/gba/fabri-rosters/agencies/support-macro-writer/workspace/tickets/example.txt:1-8`).
The old training runs show this evidence boundary is within the company's competence: one says,
“Do not characterize this as a confirmed duplicate-charge incident until the billing records are
reviewed” (`benchmarks/results/run-logs-2026-07-22/per-run/support-hq/study-memory-training__replica-01.md:28-31`).

### (b) The new holdout situation

The holdout asks both crews to handle the operational event in the incident workspace under the
previously established protocol. It does not say what happened. The incident investigator can read
and grep its workspace (`/Users/rushour0/gba/fabri-rosters/agencies/incident-postmortem-crew/investigator.openai.yaml:5-15`),
whose fixed timeline supplies customer HTTP 500 impact, rollback, baseline recovery, and an
internal configuration cause (`/Users/rushour0/gba/fabri-rosters/agencies/incident-postmortem-crew/workspace/incident/timeline.md:1-7`).
The root must select the second protocol branch and synthesize customer copy.

The prior logs demonstrate both halves are runnable. The memory arm produced “We rolled back the
affected release, and checkout service has been restored”
(`benchmarks/results/run-logs-2026-07-22/per-run/support-hq/study-memory-holdout__replica-01.md:16-20`),
while a no-memory control produced an equally polished update
(`benchmarks/results/run-logs-2026-07-22/per-run/support-hq/study-control-holdout__replica-04.md:14-16`). The new instrument deliberately does
not score that generic prose competence.

### (c) Why this is application, not recitation

The training record's applied values are `REPORT_ONLY / DIRECT_REPLY / CUSTOMER_FACTS /
VERIFY_ACCOUNT`. Every scored holdout value is different. Repeating the training JSON fails all
four fields. Passing requires recognizing a different evidence pattern—service impact, observed
mitigation, absent permanent-remedy evidence—and selecting the other learned branch. The outward
copy is also for a service event rather than an individual billing report.

### (d) Control-agent bound

The control can read the incident timeline, delegate both capable crews, and produce a safe,
empathetic update. Existing control output proves that. It cannot recover the private names or the
four-axis mapping of `SHQ-E1`, because neither company config nor workspace fixture contains them
and its holdout memory DB is absent. My paper estimate is a **3% control pass rate** for exact
four-field equality (plausible range 0-10%).

I would be wrong if the structured-output schema leaks the enum values/constants, if the holdout
prompt is augmented with the training protocol outside the DB, or if a model happens to reproduce
all four identifiers from latent convention-like guesses. I could also be wrong in the opposite
direction: if mining drops the mapping or retrieval misses it, the memory arm will fail too. The
paid smoke should inspect the retrieved lesson and the final structured object, not just prose.

## `reliability_labs_incident_release_gate`

### (a) What the training run establishes

Training asks the QA crew to assess its isolated `src/cart.py` module and establishes the `RL-G2`
two-key release protocol:

- `gate` is `OPEN` only when relevant test execution passes and every applicable production
  runtime preflight has evidence; otherwise it is `SEALED`.
- `production_evidence` is `NOT_APPLICABLE`, `VERIFIED`, or `UNVERIFIED` based on integration
  scope and actual preflight evidence.
- `rollback_role` is `NOT_APPLICABLE`, `CONTAINMENT_ONLY`, or `REMEDIATION_PROOF`; recovery after
  rollback without a validated corrected deploy is only containment.

Training applies the protocol to an isolated local-module assessment; it does not apply the
production-incident branch scored in the holdout. The exact mapping is written to root memory.

Reliability Labs really has incident, bug-triage, and QA reports
(`/Users/rushour0/gba/fabri-rosters/companies/reliability-labs/company.toml:15-33`). The QA manager
can delegate test writing and execution (`/Users/rushour0/gba/fabri-rosters/agencies/qa-automation-crew/agent.openai.yaml:5-23`),
the writer can inspect and write tests (`/Users/rushour0/gba/fabri-rosters/agencies/qa-automation-crew/writer.openai.yaml:5-15`), and the runner can execute
them but is explicitly prohibited from claiming an unrun pass (`/Users/rushour0/gba/fabri-rosters/agencies/qa-automation-crew/runner.openai.yaml:5-15`). Its
fixed module has ordinary and validation behavior that can be inspected
(`/Users/rushour0/gba/fabri-rosters/agencies/qa-automation-crew/workspace/src/cart.py:1-10`). Thus the
training calibration is reachable; whether the generated tests actually execute is intentionally
not part of the holdout rubric.

### (b) The new holdout situation

Holdout asks all three crews to apply the prior gate to the checkout release evidence distributed
across their workspaces. The incident timeline documents a rollback and baseline recovery but no
corrected deploy (`/Users/rushour0/gba/fabri-rosters/agencies/incident-postmortem-crew/workspace/incident/timeline.md:3-7`). Bug triage has
a separate, fixed discount error—`discount_percent` is subtracted as a fraction
(`/Users/rushour0/gba/fabri-rosters/agencies/bug-triage-crew/workspace/store.py:1-3`)—and a test that
expects 10% off 100 to equal 90 (`/Users/rushour0/gba/fabri-rosters/agencies/bug-triage-crew/workspace/test_store.py:1-5`). The triage
manager has investigator, fixer, and tester reports with read/edit/bash capabilities
(`/Users/rushour0/gba/fabri-rosters/agencies/bug-triage-crew/agent.openai.yaml:5-30`; `/Users/rushour0/gba/fabri-rosters/agencies/bug-triage-crew/triager.openai.yaml:5-15`;
`/Users/rushour0/gba/fabri-rosters/agencies/bug-triage-crew/fixer.openai.yaml:5-15`; `/Users/rushour0/gba/fabri-rosters/agencies/bug-triage-crew/tester.openai.yaml:5-15`).

Existing output shows the company can synthesize this evidence: “Do not release,” with the code
defect, rollback, missing configuration, and absent test evidence distinguished
(`benchmarks/results/run-logs-2026-07-22/per-run/reliability-labs/study-memory-holdout__replica-04.md:16-26`).
The corresponding control also produced a correct generic no-release recommendation
(`benchmarks/results/run-logs-2026-07-22/per-run/reliability-labs/study-control-holdout__replica-01.md:16-26`), which is why prose terms are not
the new required score.

### (c) Why this is application, not recitation

Training calibrates an isolated-module assessment, where production configuration and rollback can
be `NOT_APPLICABLE`. Holdout requires classifying a production-integrated incident with an
unverified runtime prerequisite and rollback-only recovery. Copying the training record cannot
produce `UNVERIFIED` or `CONTAINMENT_ONLY`. Even if a holdout crew repairs or tests local code, the
fixed incident evidence still contains no production preflight or corrected production deploy, so
all three expected fields remain deterministic.

### (d) Control-agent bound

The control can and probably will recommend no release; historical controls already do. It cannot
know that Reliability Labs previously chose the names `SEALED`, `UNVERIFIED`, and
`CONTAINMENT_ONLY`, or that these are the three axes of `RL-G2`. My estimate is a **5% control pass
rate** for exact three-field equality (plausible range 0-15%). It is slightly higher than Support
HQ because “unverified” is natural language a strong model might guess.

This estimate is wrong if the response schema reveals the expected enums, if generic model priors
happen to match the identifiers, or if some non-DB artifact carries the training prompt. Memory
could also underperform if the opaque convention is not mined/retrieved. A smoke should additionally
verify that the holdout result remains `SEALED` regardless of whether local tests ran.

## `revenue_ops_evidence_backed_outreach`

experiment and establish the `REV-E2` evidence-routing convention:

  segment research is `MARKET_PROXY`; aggregate rows are `AGGREGATE_ONLY`; use

- `outreach_mode` is `DISCOVERY_1TO1` only when a direct profile gives a named role/problem cue;

## Closing risks and what could not be verified

1. **No behavioral validation.** I could not run the requested paid two-replica smoke, inspect a
   newly mined SQLite DB, or establish memory/control pass rates. All rate estimates above are
   guesses. The smoke should be treated as a falsification test, not confirmation.
2. **Structured-output plumbing is incomplete in the inspected tree.** The dataset key, memory
   study loader, evolution loader, response schema, and scorer must agree. The schema may describe
   key types and allowed identifier format, but must not disclose the expected branch values or
   constants to the holdout agent. A schema built directly from `expected.structured_fields` would
   contaminate the control.
3. **Mining/retrieval may prefer natural lessons over opaque enums.** Each training prompt therefore
   requires the exact convention in the root `AGENT_MEMORY` block, but I could not verify that the
   miner preserves all axes or that top-5 retrieval surfaces them. If two replicas show retrieval
   misses, simplify one axis at a time; do not add the answer to the holdout.
4. **The test intentionally includes vocabulary memory.** Exact enum names create headroom, but no
   case passes on vocabulary alone: every scored holdout branch differs from the branch applied in
   training. This is the guard against a recitation benchmark. Still, manual review should confirm
   the retrieved lesson is being applied rather than a leaked schema being copied.
5. **Static fixtures limit novelty.** Fresh compilation restores the same source fixtures. These
   designs make the task new by giving training and holdout different operational scopes and applied
   branches, not by introducing new files (which the transport contract forbids). A future stronger
   benchmark could compile condition-specific read-only fixtures, but that is outside this task and
   would require benchmark code changes.
6. **Forbidden strings remain a narrow safety net.** They catch known sensitive identifiers or
   known aggregate metrics, not every semantic fabrication. Reliability's false-resolution phrases
   can still be vulnerable to negated wording if the deployed forbidden matcher regresses from the
   current negation-aware implementation (`src/fabri/benchmarks/company_setup_probe.py:974-999`). Structured fields
   should be the required decision source; manual smoke review should check prose consistency.
7. **Evolution cannot be resumed halfway.** The old variants are answer-bearing and must not be
   mixed with these anchors. Freeze the three revised prompts only after the anchor passes the
   structured-output and retrieval smoke, then compare generations on the full revised trio.

## What surprised me

- The company compiler already provides a strong institutional-memory affordance: it explicitly
  asks the root to retain durable decisions/preferences and copies that shared DB intact. The
  experiment's transport was better designed than its old prompts.
- The no-memory controls are genuinely competent. Support produced a polished safe incident note,
  Reliability produced the correct no-release decision, and Revenue Ops correctly separated the
  aggregate dataset from the account. This makes “good prose” almost unusable as the treatment
  signal; the benchmark needs a prior convention with an application step.
- The three crews in Reliability Labs do not share one coherent code fixture: incident evidence,
  the triage discount bug, and QA's separate `cart.py` live in different agency workspaces. The old
  prompt nevertheless elicited a credible executive gate. That is impressive synthesis, but it
  also means a rubric must avoid volatile fields such as whether a local repair/test happened.
- Revenue Ops' historical qualitative failure is already visibly repaired in the roster: both
  verbose market roles now have 2048 output tokens. The remaining benchmark defect is measurement,
  not an unreachable task.
