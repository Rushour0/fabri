# R1 — Audit of `score_text()` against 118 archived agent outputs

## Scope and bottom line

I parsed all 118 logs. Only 58 have applicable rubric terms and verdicts: 32 Support HQ, 24 Reliability Labs, and 2 Revenue Ops. The other 60 are training logs (`30` memory and `30` control); `index.json` records `raw_pass: null` for them, and the extraction code deliberately supplies no rubric. They are part of the archive but are not inputs to `score_text()`.

I executed the exact current `score_text()` function body from `src/fabri/benchmarks/company_setup_probe.py` against every one of the 58 score-bearing `## Final output` sections, using `rubric_terms.json` to select holdout or evolution-variant terms. Results:

- Archived raw scorer: **47/58 pass**.
- Archived negation-corrected scorer: **55/58 pass**.
- Current `score_text()`, containing both known fixes: **56/58 pass**.
- Current versus archived corrected differs once: `reliability-labs/study-control-holdout__replica-06.md`, the already-known long-distance negation case. I do not count it as a new finding.
- Manual semantic audit of all 56 current passes found **2 false passes**. Manual audit of the 2 current failures found **2 false failures**.

Correcting those four real-corpus errors happens to leave the overall total at 56/58, but it materially redistributes the arm results: Reliability evolution candidate goes 3/3 → 2/3, Reliability evolution incumbent 3/3 → 2/3, Reliability study-control holdout 8/9 → 9/9, and Revenue Ops study-memory holdout 0/1 → 1/1. The unchanged aggregate is therefore misleading.

The ranking below prioritizes demonstrated corpus movement, then plausible false-pass exposure. “Observed” distinguishes a wrong real verdict from a merely visible match dependency.

## 1. Required terms are polarity/evidence blind — real false passes

The scorer asks only whether `rollback` occurs. It does not ask whether the output reports the confirmed rollback evidence requested by the prompt, denies it, or says it is unavailable.

### Real corpus evidence A

The `qa_release_summary` prompt says: “Include confirmed rollback evidence” (`benchmarks/datasets/company_memory_experiments.yaml:133-136`). The output instead says:

> “**Rollback status:** No crew provided executed rollback logs, deployment records, or passing rollback test results. Therefore, rollback completion is **not confirmed**...”

Artifact: `benchmarks/results/run-logs-2026-07-22/per-run/reliability-labs/evo-candidate__replica-01__qa_release_summary.md:19`.

The current scorer nevertheless printed:

```text
reliability-labs/evo-candidate__replica-01__qa_release_summary.md {'passed': True, 'missing': [], 'forbidden': []}
```

This is a false pass: the exact required fact is denied, while its noun supplies the required token.

### Real corpus evidence B

The `deployment_gate_brief` prompt asks the output to distinguish “rollback facts from outstanding production verification” (`company_memory_experiments.yaml:123-127`). Its only rollback fact is an absence claim:

> “**Rollback facts:** No rollback action, deployment history, or rollback result is evidenced.”

Artifact: `benchmarks/results/run-logs-2026-07-22/per-run/reliability-labs/evo-incumbent__replica-01__deployment_gate_brief.md:19`.

The current scorer printed:

```text
reliability-labs/evo-incumbent__replica-01__deployment_gate_brief.md {'passed': True, 'missing': [], 'forbidden': []}
```

The output is appropriately conservative, but it does not supply the requested rollback facts available elsewhere in this fixed scenario. Presence scoring cannot distinguish that omission from compliance.

### Minimal reproduction actually run

```text
text = 'Checkout: no rollback occurred. Verification is pending.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

Terms were Reliability holdout required `checkout`, `rollback`, `verification`, with no forbidden terms. This is distinct from the known forbidden-negation bug: it is the **required** side ignoring polarity.

## 2. Entity aliases/coreference are rejected — real false failure

The Revenue memory holdout is unmistakably a recommendation for the intended person and company. It says:

> “The activation-channel data is not attributable to Northstar Labs or Maya...”
>
> “Hi Maya,”
>
> “I saw your comments about standardizing onboarding as Northstar Labs has grown...”

Artifact: `benchmarks/results/run-logs-2026-07-22/per-run/revenue-ops/study-memory-holdout__replica-04.md:16,22,24`.

In an email to a named recipient, a first-name salutation plus the correct company and topic is normal and unambiguous. The output satisfies the task for Maya Chen, but the scorer requires the literal adjacent full name somewhere in the answer:

```text
revenue-ops/study-memory-holdout__replica-04.md {'passed': False, 'missing': ['Maya Chen'], 'forbidden': []}
```

Minimal reproduction actually run:

```text
text = 'Recommendation for Northstar Labs onboarding. Hi Maya, let us compare approaches.'
output = {'passed': False, 'missing': ['Maya Chen'], 'forbidden': []}
```

This single error changes the only Revenue memory holdout result from 0/1 to 1/1. That arm is too small for a rate claim, but it demonstrates that the literal-name rubric can invert the result of a semantically correct personalized email.

## 3. Morphological equivalents are rejected — real false failure

Reliability control replica 02 contains the exact requested action:

> “**Verify missing production configuration:** confirm the required payment-provider environment variable is present...”

It also provides the rollback evidence and a no-go checkout recommendation. Artifact: `benchmarks/results/run-logs-2026-07-22/per-run/reliability-labs/study-control-holdout__replica-02.md:16-28`, especially line 24.

The holdout rubric contains only `verification`, so the verb `verify` does not match:

```text
reliability-labs/study-control-holdout__replica-02.md {'passed': False, 'missing': ['verification'], 'forbidden': []}
```

Minimal reproduction actually run:

```text
text = 'Checkout rollback. Verify the production configuration.'
output = {'passed': False, 'missing': ['verification'], 'forbidden': []}
```

This is especially arbitrary because all three Reliability evolution variants explicitly use the OR-group `[verification, verify]`, while the otherwise equivalent holdout rubric does not. It is rubric phrasing, not output quality, that makes the holdout fail.

## 4. Presence checks omit task relations and deliverable requirements — algorithmic only

The rubrics test three required groups, not whether the output is the requested artifact. They do not score, for example:

- Support: acknowledgment of customer impact, customer-safe framing, or an actual promise to update.
- Reliability: a release-readiness decision or tying the missing production configuration to a verification gate.
- Revenue: an outreach recommendation, evidence boundaries, or whether any claimed intent/result is sourced.

Minimal Support reproduction actually run:

```text
text = 'Checkout rollback follow-up.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

That keyword list is not a customer-safe executive update, yet it fully passes the Support holdout rubric. Equivalent three-token lists pass the other two rubrics. I found no real corpus output whose only defect was one of these omitted deliverable requirements; the 56 current passes were substantive responses. This is therefore a demonstrated instrument ceiling, not a claimed corpus-rate correction.

## 5. Forbidden concepts are evadable by synonyms/paraphrases — algorithmic only

Forbidden matching is literal after normalization. Ordinary semantic equivalents are invisible.

Minimal Reliability reproduction actually run:

```text
text = 'Checkout rollback verification complete. The remediation is live in production.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

“The remediation is live in production” makes the prohibited production-resolution claim without containing `fix was deployed` or `resolved in production`.

Minimal Revenue reproduction actually run:

```text
text = 'Maya Chen at Northstar Labs has clear purchase intent around onboarding.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

`purchase intent` is an ordinary equivalent of forbidden `buying intent`. A real lexical variant appears in the Revenue memory log—“Do not cite ... **purchasing intent**: the available material does not substantiate them” (`revenue-ops/study-memory-holdout__replica-04.md:16`)—but it is correctly negated, so it does not create a wrong real verdict. The adversarial positive form shows the false-pass path.

## 6. Negation scope overreaches — algorithmic false-pass path

The known bug was the opposite direction: a truly negated forbidden phrase was treated as positive. The current code fixes that case, but its scope rule introduces a separate false-pass class. Any cue anywhere before the term, back to a punctuation/newline boundary and at most 400 characters, suppresses the hit. It does not establish that the cue governs the forbidden phrase.

Minimal reproduction actually run:

```text
text = 'Checkout rollback verification. Not only was testing completed, the fix was deployed.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

`not` belongs to the positive construction “not only”; the sentence plainly asserts that the fix was deployed. The scorer suppresses it anyway. I inspected all nine real occurrences of `fix was deployed`; every one was genuinely negated, so this class did not change a corpus verdict.

## 7. OR-groups can match an incidental sense — real phrasing dependency

Support control replica 05 says:

> “We are monitoring performance and conducting a **follow-up review** to strengthen safeguards... We will share any additional customer-relevant updates as appropriate.”

Artifact: `benchmarks/results/run-logs-2026-07-22/per-run/support-hq/study-control-holdout__replica-05.md:20`.

The required OR-group is `[follow-up, further update]`. The scorer passes on the internal activity “follow-up review,” not on the actual customer promise “share ... updates.” The singular/plural and missing `further` mean that the latter does not match. The same dependency occurs in `support-hq/study-memory-holdout__replica-05.md:18`.

I ran both archived outputs, then changed only `follow-up review` to the semantically equivalent `post-incident review`:

```text
study-control-holdout__replica-05.md
 archived = {'passed': True, 'missing': [], 'forbidden': []}
 only_incidental_phrase_changed = {'passed': False, 'missing': ['follow-up | further update'], 'forbidden': []}
study-memory-holdout__replica-05.md
 archived = {'passed': True, 'missing': [], 'forbidden': []}
 only_incidental_phrase_changed = {'passed': False, 'missing': ['follow-up | further update'], 'forbidden': []}
```

Both real outputs do promise a later customer update, so their human pass verdicts are sound. The match provenance is nevertheless wrong and phrasing-lucky. The false-pass version is easy to demonstrate:

```text
text = 'Checkout was restored after rollback. We are conducting a follow-up review.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

That text offers only an internal review, not the requested customer follow-up.

## 8. Five-token proximity joins unrelated entities — algorithmic only

The ordered window is not a phrase or relation matcher. Each later token may occur up to four token positions after the prior one, so distinct subjects/objects can be joined.

Minimal reproduction actually run:

```text
text = 'Maya briefed Alex before Chen responded. Northstar competed against Acme Labs. Onboarding is discussed.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

The scorer constructs `Maya Chen` from two people and `Northstar Labs` from two organizations. This is beyond the known proximity bug: proximity now finds separated wording, but the allowed window has no syntactic or entity constraint. All real Revenue multi-word matches were adjacent and correct; no corpus verdict moved.

## 9. Single-word substring matching has no token boundaries — algorithmic only

Both required and forbidden single words match inside larger words.

False-pass reproduction actually run:

```text
text = 'Checkoutless status: rollbackless and verificationless.'
output = {'passed': True, 'missing': [], 'forbidden': []}
```

False-failure reproduction actually run with the Support rubric:

```text
text = 'A blameless checkout update says the rollback is complete and promises a follow-up.'
output = {'passed': False, 'missing': [], 'forbidden': ['blame']}
```

`blameless` asserts the opposite of assigning blame, but it contains the forbidden substring. No such embedded-word collision occurs in the 58 scored logs.

## 10. Presentation punctuation/newlines become semantic boundaries — algorithmic only

Multi-word required matching splits on `[.!?\n]+`. A Markdown hard wrap or an abbreviation period can split a visibly continuous name. Minimal reproductions actually run:

```text
text = 'Maya\nChen works at Northstar Labs on onboarding.'
output = {'passed': False, 'missing': ['Maya Chen'], 'forbidden': []}

text = 'Maya A. Chen works at Northstar Labs on onboarding.'
output = {'passed': False, 'missing': ['Maya Chen'], 'forbidden': []}
```

I specifically checked the real bullet lists, bold headings, tables, numbered lists, and line breaks. They did not cause a verdict error here. The two current real failures are explained completely by alias rigidity and `verify`/`verification`, not Markdown splitting.

## Clean areas

- **Corpus/accounting:** all 118 logs map one-to-one to `index.json`; 58 are rubric-bearing and 60 training outputs are intentionally unscored. I found no missing or duplicate archived log.
- **Re-score consistency:** current `score_text()` agrees with archived corrected verdicts on 57/58 scored logs. The sole difference is the already-documented Reliability control replica 06 long-distance negation correction.
- **Repeated forbidden occurrences:** the loop does not let one negated occurrence hide a later positive occurrence. The executed check `No fix was deployed. Later the fix was deployed.` returned `{'passed': False, 'missing': [], 'forbidden': ['fix was deployed']}`.
- **Basic proximity limits:** order, sentence boundaries, and maximum distance work as coded. `Maya spoke. Chen replied...` and `Maya one two three four Chen...` both returned missing `Maya Chen`; the false-positive class requires tokens to fit inside the allowed local window.
- **Hyphen/compact handling:** the executed `Checkout rollback followup.` check satisfied required `follow-up`, as intended.
- **Forbidden semantics in the real corpus:** all nine current matches for `fix was deployed` were genuinely negated. I found no real false pass caused by negation overreach or an uncaught positive forbidden synonym.
- **Support output quality:** all 32 scored Support outputs substantively acknowledge the checkout incident, report rollback, and provide a future-facing update while avoiding internal configuration and blame. The two `follow-up review` cases are match-provenance defects, not bad outputs.
- **Known bugs:** I did not rank or relabel the already-known forbidden-negation false positives or the already-fixed strict required-phrase matching problem.

## What surprised me

The largest surprise is that fixing the four newly observed semantic verdict errors leaves the aggregate at exactly 56/58: two false passes and two false failures cancel numerically. At the arm level they do not cancel at all. The sole Revenue memory run flips from fail to pass, Reliability control becomes 9/9, and each Reliability evolution generation loses one pass.

The two evolution false passes are mirror images: one says rollback is “not confirmed,” the other says no rollback action is evidenced, yet both score identically to outputs containing the actual rollback timeline. Meanwhile, a strong evidence-bounded Revenue email fails only because normal email style says “Hi Maya” rather than restating “Maya Chen.”

Finally, the most revealing phrasing-luck case was not exotic adversarial prose. Two normal Support outputs pass because “follow-up” modifies an internal **review**; their genuine promise to share customer **updates** is invisible to the holdout OR-group. That is a concise example of why a correct total can still be produced by the wrong proof.
