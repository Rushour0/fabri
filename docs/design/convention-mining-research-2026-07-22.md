# Convention mining for fabri's memory engine

**Date:** 2026-07-22  
**Status:** design research only; no implementation changes included  
**Scope:** declared, reusable conventions and multi-branch protocols—not fixes to
`<!-- AGENT_MEMORY -->` emission

## Problem statement

The [headroom smoke diagnosis](../../benchmarks/results/headroom-smoke-diagnosis-2026-07-22.md)
shows that fabri can transport and retrieve a sufficiently long lesson, yet still loses because
the miner stores the branch used in training rather than the full protocol declared for later
work. The declaration is present in the `start` event's task text, but the success miner reduces a
run to one four-clause, token-capped lesson about what happened. Increasing the lesson cap can
preserve a longer applied branch; it cannot make an episodic success summarizer select an
unapplied branch it was never asked to preserve. Fabri therefore needs a separate path for
declared semantic/procedural knowledge, with an explicit trust gate because task text is an
attacker-controlled input.

## Prior-art survey

These notes are from prior knowledge only, as required; they were not network-verified in this
research pass. Product APIs and terminology may have changed, and uncertain details are marked.

**Letta / MemGPT.** MemGPT's central idea, continued by Letta, is virtual context management:
small, editable **core-memory blocks** stay in the prompt, while larger **archival memory** stays
outside the context window and is searched or paged in when relevant; conversation history is a
separate recall surface. This is a useful distinction for fabri: a compact, verified convention
can behave like scoped core memory, while run traces and applied-branch observations remain
archival/episodic. It also argues against compressing a durable policy and an episode into the same
record. I am uncertain which current Letta release names every storage tier exactly this way, but
the core-versus-archival separation is foundational to the MemGPT/Letta design.

**mem0.** mem0 generally extracts candidate facts from conversations, compares them with existing
memories, and chooses operations such as add, update, delete, or no-op before storing searchable
records with user/agent/run scoping and metadata. Its useful lesson here is that semantic memory is
maintained as an evolving fact set rather than as a summary of every episode: extraction and
conflict resolution are first-class stages. It is less useful as a ready-made protocol model;
from my knowledge, its common memory record is still primarily free text plus metadata, so
conditional branch completeness would need a fabri-specific schema. Exact current operation names
and graph features are version-sensitive and therefore uncertain.

**Zep.** Zep's newer memory architecture uses a temporal knowledge graph (associated with
Graphiti): source episodes are ingested, while entities, relationships, and facts are derived with
temporal validity so later facts can supersede earlier ones without erasing history. That
episode-versus-derived-fact split maps cleanly to fabri's need to retain the declaring span and a
separate canonical convention, and temporal edges suggest `valid_from`, `invalid_at`, and
`supersedes` rather than hit-count-based staleness. Zep does not, to my knowledge, provide a
drop-in representation for an ordered multi-branch decision table; the relevant prior art is its
provenance and temporal conflict model, not its final prompt format.

**LangMem.** LangMem explicitly discusses semantic memory (facts), episodic memory (past
experiences), and procedural memory (instructions or behavior), with both in-the-hot-path tools and
background memory-management flows over namespaced stores. The important distinction is that a
declared protocol is procedural/semantic content, whereas “branch A worked in this run” is
episodic evidence; the former should not be regenerated by compressing the latter. LangMem also
supports schema-shaped memories rather than requiring one universal prose record, which supports a
typed `convention` payload and a kind-specific renderer in fabri. I am uncertain about the exact
current public API names for its background manager, so this paragraph relies only on the stable
conceptual categories.

## Detection trade-off

The miner should inspect all three available surfaces, but it should not treat them as equally
authoritative:

- The `start.task` text is the primary declaration source because it can contain every branch
  verbatim. It is also untrusted and grants no durable authority by itself.
- Trace events can corroborate which branch was applied and whether the run completed. They cannot
  validate an unexercised branch merely because another branch succeeded. Tool output may be a
  declaration source only when the tool itself has trusted provenance; arbitrary retrieved content
  remains untrusted.
- Final-answer text is model-generated. It can help locate a named convention or record an applied
  branch, but it must not upgrade authority or replace missing task-text branches. The separate
  `AGENT_MEMORY` workstream remains useful if emission improves, but this design does not depend on
  it.

| Detector | Runtime cost | Strength | Main weakness |
|---|---:|---|---|
| Deterministic only | No model call; linear text scan and parse | Auditable, reproducible, exact for a constrained grammar | Misses natural-language declarations and paraphrased conditions |
| LLM on every mined run | One extra extraction call per run, with input-token cost proportional to supplied text; adds model latency | Highest linguistic recall | Pays on irrelevant runs and creates an opaque, injection-exposed interpretation step |
| Deterministic gate + LLM extraction | No model call on gate-negative runs; one bounded call on candidate-positive runs | Good recall with bounded cost and an auditable first stage | Still needs strict validation because the LLM can omit, merge, or invent branches |

A useful deterministic gate looks for a conjunction of signals rather than one magic phrase:
future reuse language (`establish`, `for later`, `from now on`), a stable name or key, normative
language (`must`, `map`, `when/if`), and at least two condition/outcome clauses or a table-like
mapping. The gate should return source spans, not a yes/no label. Those spans—not an entire raw
trace—become quoted data for any LLM extractor, keeping both cost and prompt-injection surface
bounded.

## Design options

### Option 1 — Strict deterministic convention grammar

**Detection mechanism.** Recognize only a documented mini-language or strongly structured task
form, such as a named protocol followed by `IF <condition> THEN <field>=<value>` branches. Parse it
without an LLM and require a stable name, scope, at least two branches, and complete field sets.
Natural-language declarations that do not parse are reported as skipped candidates.

**Schema changes.** Add `kind="convention"` and a structured payload containing `key`, `version`,
`scope`, ordered `branches[{when, set}]`, source span/hash, authority, and lifecycle metadata.
Give it a separate ID namespace and exact canonical dedup key. Do not send it through cross-kind
cosine dedup, tactical-to-strategic promotion, generic token compression, or grouped eviction
summarization.

**Retrieval changes.** Index a complete, deterministic summary in `entry.text`, but render from the
structured branches in a dedicated `<retrieved_conventions>` block. Retrieve by scope, exact name,
keywords, and embedding relevance; inject the complete bounded decision table so the model cannot
mistake the observed branch for the only branch.

**Injection-risk posture.** Parsing does not establish trust. Task-origin records enter
`tier="quarantine"` explicitly and remain excluded until an authorized source or human approves
them. Arbitrary prose and executable capabilities are invalid grammar.

**Rough effort:** **M** in the engine, plus documentation/adoption work for task authors.

**What could go wrong.** Recall will be low for existing natural-language tasks, authors may learn
to write to the parser, and a syntactically valid malicious declaration still needs the same
authority gate. A permissive grammar would gradually recreate an LLM parser badly.

### Option 2 — Hybrid candidate detection plus typed LLM extraction

**Detection mechanism.** Run the deterministic gate above over task spans, trusted tool-result
spans, and convention-like final-answer spans. Send only positive spans and nearby context to an
LLM that must emit a typed candidate. Validate that every protocol name, condition, field, and
literal value is source-anchored; reject or quarantine incomplete/ambiguous parses. Trace evidence
is attached separately as branch coverage, never used to synthesize absent branches.

**Schema changes.** Add the same first-class `convention` kind and structured payload as Option 1,
plus extraction metadata (`extractor`, schema version, source-span hashes, completeness, and reason
codes). Use a separate configurable convention budget—on the order of 256–512 tokens is a
reasonable starting range for evaluation—not `guideline_max_tokens`. If a complete record exceeds
the limit, reject/quarantine it; never truncate a branch.

**Retrieval changes.** Add kind-aware rendering rather than flattening every hit to
`entry.text`. Rank on a complete index text, filter by authority/version/scope, reserve a bounded
convention slot, and render all branches by default. A deterministic selector may highlight one
branch only when its predicate is machine-evaluable; otherwise the model receives the whole table
and an explicit “choose exactly one branch from current evidence” rule.

**Injection-risk posture.** All task- and model-origin candidates start quarantined even if the run
succeeded. Promotion requires durable-memory authority, exact extraction checks, no unresolved
same-key conflict, and an allowed effect class. High-impact or action-bearing content cannot be
promoted through this path.

**Rough effort:** **L**. The extractor is straightforward; schema-safe lifecycle, conflict handling,
renderer changes, evaluation fixtures, and review surfaces are the larger work.

**What could go wrong.** The extractor can silently normalize away a meaningful distinction,
conditions can be semantically ambiguous, and a superficially source-anchored malicious protocol
can still be harmful. LLM/version drift also makes extraction less reproducible unless candidates
and reason codes are retained for replay.

### Option 3 — Trusted declaration event or registry

**Detection mechanism.** Do not infer conventions from ordinary task text. A trusted compiler,
company manifest, or operator emits a typed `CONVENTION_DECLARED` event/record with branches,
scope, version, and authority. Traces merely attach observations to that registered convention.

**Schema changes.** Use the same structured convention payload, but make issuer identity and
version/supersession mandatory. The source event or manifest is canonical; `entry.text` is a
derived search index only.

**Retrieval changes.** Use the same dedicated resolver and renderer as Option 2. Trusted scope and
version make conflict filtering simpler, and high-confidence exact-key retrieval can precede
semantic retrieval.

**Injection-risk posture.** Strongest option: ordinary task text can reference a registered
convention but cannot create one. The producer boundary must be authenticated; otherwise the new
event is only a more convenient injection format.

**Rough effort:** **L end-to-end**: **M** for engine support and additional work in every producer,
compiler, or authoring surface.

**What could go wrong.** It does not solve passive mining for arbitrary tasks, adoption may be as
weak as current optional self-reporting, and convention updates can bypass memory if upstream
producers do not emit the event. It is best as an authority path, not the sole detector.

## Recommendation

Build **Option 2 behind a default-off flag**, while adopting Option 3's trusted producer contract
as the strongest promotion path. This gives passive mining useful recall without pretending that
task text is durable policy. Deterministic-only parsing is a valuable fast path and validation
layer, but too narrow to be the only way an existing company declares conventions; LLM-only
extraction is needlessly expensive and gives the least auditable boundary.

### Recommended record and lifecycle

A convention should be one atomic record, conceptually:

```yaml
kind: convention
text: "SHQ-E1 support evidence response mapping: DECLARED…; MITIGATED…"
convention:
  key: SHQ-E1
  version: "1"
  scope: {company: support-hq, domain: customer-evidence}
  branches:
    - when: "<source-anchored condition A>"
      set: {evidence_state: "<A value>", response_mode: "<A value>"}
    - when: "<source-anchored condition B>"
      set: {evidence_state: "<B value>", response_mode: "<B value>"}
  source:
    channel: task
    event_ids: ["<start-event-id>"]
    span_hash: "<hash>"
    authority: untrusted_task
  status:
    extraction: source_anchored
    branch_coverage: [A]
    supersedes: null
    expires_at: null
```

The exact fields are a design sketch, not a proposed wire format. Three distinctions are
load-bearing:

1. `entry.text` is a complete search index, not the canonical payload and not the only injected
   representation.
2. Extraction fidelity, source authority, and observed branch coverage are separate facts. A
   clean run applying branch A can support `branch_coverage=[A]`; it cannot verify branch B or grant
   the issuer durable authority.
3. `verification` continues to express evidence/trust and `tier` continues to express placement.
   A new task-declared convention must be explicitly quarantined; the current generic tier
   classifier would otherwise classify an unverified non-`success_pattern` kind as retrievable.

Dedup must be exact and version-aware: hash `(scope, key, version, canonical branch mapping)`.
Exact matches merge provenance and coverage. The same `(scope, key, version)` with a different
mapping is a conflict to quarantine, never a cosine duplicate and never a “keep the longer text”
merge. A declared newer version may supersede an older version only when the issuer is authorized.

Staleness should be semantic rather than episodic. Verified conventions expire through explicit
`expires_at`, issuer revocation, contradiction, or a trusted `supersedes` relation; low retrieval
count alone is not evidence that a policy is stale. Convention records need a separate bounded
quota, and generic eviction summarization must never turn several decision tables into one
tactical sentence. When a size limit is hit, retain canonical records according to authority,
version, and freshness, and produce a reviewable eviction decision rather than lossy compression.

### Recommended retrieval and branch application

Retrieval should split ranking from rendering:

1. Search the complete convention index using exact protocol names, scope, hybrid lexical/vector
   relevance, and current-task terms.
2. Exclude quarantine, contradicted, expired, superseded, wrong-scope, and unauthorized entries
   before they compete for a prompt slot.
3. Resolve same-key versions/conflicts, then render eligible conventions from their structured
   payload in a separate fenced block. Keep every branch and its condition within one atomic
   record; use a convention-specific character/token bound rather than the current 500-character
   guideline truncation.
4. Preselect a branch only for machine-evaluable predicates. Otherwise inject the complete small
   decision table, tell the model to choose exactly one branch from current evidence, and preserve
   the condition beside every output mapping. If conditions overlap or none match, the safe result
   is “not applicable/ambiguous,” not a best-effort branch blend.

This is deliberately not an always-injected global policy tier. Conventions should be scoped and
retrieved just in time first; a later “core” promotion can reserve prompt space only after
recurrence, authority, conflict, and retrieval-quality evaluation justify it.

### Security and interaction with ActionMemory

Task authority for the current run is not durable-memory authority. Before a convention can steer
a future run, all of the following must be true:

- Its issuer is authorized for the stored scope (for example, trusted company config/manifest or
  explicit human approval); repeated attacker-controlled tasks do not become authority through
  recurrence.
- Its structured mapping is complete and source-anchored, its version is current, and it has no
  unresolved same-key contradiction. Operational success or `rubric_verified` on one applied
  branch is not enough to validate the full declaration.
- Its effect class is permitted for convention injection. Response-field mappings and bounded
  workflow choices may be eligible; credential changes, policy override, external side effects,
  tool/config mutation, and attempts to weaken system/current-task constraints are not.
- Retrieval scope and branch applicability match the future task. Sanitization, delimiter
  escaping, size bounds, current-task precedence, and provenance logging remain defense in depth,
  not substitutes for authority.

Every detected task-text convention should therefore start as
`verification="unverified", tier="quarantine"`, regardless of whether
`memory.tiering_enabled` is on. Quarantine is already excluded from retrieval even when tier
preference is off; convention ingestion should preserve that property explicitly. Promotion to
`retrieve` requires the authority and integrity gates above; promotion to `core` should additionally
require cross-session usefulness and an eval-gated prompt-budget decision. A convention must never
receive `tier="action"` or populate `resolution` merely because its prose asks for an action.

Severity should only tighten these gates, never substitute for trust. A low-impact response-format
mapping may be eligible for scoped retrieval after authority verification; a workflow rule with
external consequences should require stronger review; and a config/tool mutation must leave the
convention channel entirely and use typed ActionMemory. Recurrence or a high “importance” score
must not promote an untrusted declaration across those boundaries.

The fail-closed ActionMemory path remains a separate capability boundary. Convention text cannot
add a capability, choose an arbitrary config path, relax hard preconditions, or change the
idempotence/attempt/cap limits enforced by `action_execution.py`. If a declared protocol genuinely
needs automatic mutation, it must be translated into a typed ActionMemory candidate and pass that
path's independent verification and allowlist; convention retrieval alone can never auto-execute
it.

## Open questions requiring a human decision

1. **Who can create durable policy?** Is trusted company/agency configuration sufficient, or must
   every task-mined convention receive explicit human approval before leaving quarantine?
2. **Which effect classes are allowed?** Start with structured response mappings only, or also
   admit non-executable workflow conventions such as escalation and follow-up choices?
3. **How should ambiguous natural-language conditions behave?** Inject the complete table and let
   the model decide, require a machine-evaluable predicate grammar, or fail closed and ask for a
   task-local clarification?
4. **What are the convention budget and lifecycle defaults?** Choose the evaluated per-record
   token/branch limits, separate store quota, expiry policy, and who may issue `supersedes`.
5. **What evidence unlocks `core` placement?** Decide whether authorized declaration alone is
   enough for scoped retrieval, and what recurrence/branch-coverage and offline/live evaluation
   gates are required before reserving always-on prompt space.

## What surprised me

- Quarantine exclusion is unconditional at retrieval time even when tier preference is disabled;
  that is already the right fail-closed primitive for untrusted convention candidates.
- Adding only a new `kind` would be unsafe. Generic ingest could cross-kind cosine-merge it,
  promote it to `strategic`, and grouped eviction could summarize it into a `tactical` sentence,
  losing both identity and branches.
- The current tier classifier's special quarantine rule is specific to unverified
  `success_pattern` entries. An unverified `convention` would default to `retrieve` unless the new
  path assigns quarantine explicitly and adds a convention-aware classification rule.
- A larger storage cap is still insufficient because retrieval independently sanitizes each
  injected `entry.text` to 500 characters. Convention rendering needs its own atomic size policy.
- The action boundary is materially stronger than the prose-memory boundary: executable changes
  already require typed data, trusted config-derived paths, hard applicability checks, and a narrow
  allowlist. Convention mining should reuse that separation of authority, not reuse the action
  payload itself.
